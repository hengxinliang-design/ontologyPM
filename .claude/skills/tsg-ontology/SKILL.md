# TSG PM 本体工作法

这个技能做两件事：告诉你 TSG PM 的本体在哪、怎么改；以及在改之前、改之中、改之后，按什么方法保证本体不会变成一团“精致的混乱”。方法来自三篇 LLM 构建本体的论文和一篇情境感知本体的论文，已经翻译成本项目的做法，原始要点见 `references/papers.md`。

**开始任何本体任务之前，先读两份文件：**

- `references/lessons.md`（经验库）：记着本项目犯过的每一类错误和预防办法，同样的错误不应该犯第二次。
- `docs/requirements/TSG_PM_需求规格与本体基线.md`（需求基线）：业务由哪些对象、行为、规则、联动和角色组成，哪些还没确认。新需求先在这里找到位置；找不到就走工作流 F，不要直接改本体。

## 先弄清本体在本项目里是什么

本体是系统对业务世界的唯一说明书，也是页面、PM Assistant 和 API 共用的计算口径。它不是 RDF/OWL，而是 Palantir 式的 YAML 元数据加规则注册表，但每个部件都对应着论文里的标准概念：

| 本项目 | 论文中的对应概念 | 作用 |
| --- | --- | --- |
| `metadata/object-types/*.yaml` 的对象类型 | 类（owl:Class，TBox） | 业务里有哪些东西 |
| 推导规则（`derivations`、`derivedFrom`） | 规则推理（rule-based inference） | 派生属性由哪条规则算出，元数据即契约 |
| 属性的 `sourceKind` 与 `source` | 溯源（provenance）与口径说明 | 数据从哪来、怎么算 |
| `link-types.yaml` 的 source / target / cardinality | 对象属性的 domain / range | 东西之间怎么关联 |
| `metadata_schema.py`（Pydantic，`extra=forbid`）与 `compiler.py` | 结构化输出约束、SHACL 结构校验 | 不合法的元数据启动即失败 |
| 动作的 `submissionCriteria` | SHACL / 规则校验 | 不合规的写入被拒绝 |
| `ontology_versions` 版本登记与差异 | 可版本化的 TTL 工件、ontology diff | 变更可追溯、可比较 |
| `OperatingPolicy` 运营口径参数 | 规则的参数化 | 阈值作为数据保存并审计 |
| 对象实例（项目、工时……） | 个体（ABox） | 具体的数据 |
| 派生的判定（风险等级、健康状态、信号）及其依据属性 | 情境与它支持的信息单元（infon） | 判定是对关系的推断，依据写出观察到的事实和规则 |
| 运营口径参数、工作日历、年度计划 | 资源情境（背景知识） | 推理时借用的背景，回答时要说出当前取值 |

文件位置、命令和本项目踩过的坑在 `references/repo-map.md`。动手改元数据之前先读它。

## 核心原则

下面每一条都来自论文的结论，也都在本项目中验证过。理解“为什么”比记住条目更重要。

1. **LLM 生成，本体裁决。** LLM 擅长解释和起草，但不擅长长期记忆和保持一致。所以凡是会成为事实的东西（新属性、新规则、PM Assistant 推断出的结论），都先是“候选”，通过校验才进入可信的本体。校验不过的留在日志或文档里，不进入元数据，也不写库。
2. **先划定范围，再抽取。** 论文中最差的结果（金融领域 F1 只有 0.12）来自范围不清：模型自己决定哪些概念该收进来。每次扩展本体前，先写下这次要回答的问题（能力问题，competency questions），没有对应问题的概念不收。
3. **类型和实例分开。** LLM 常把具体值当成类，例如把“TSG999”做成对象类型、把“失效”做成属性。判断方法：如果它是某个对象的一个取值，就是枚举值、配置数据或对象实例，不是对象类型。
4. **关系要有方向和严格的含义。** 论文观察到模型会把父子方向弄反，或用含糊的“isTypeOf”。本项目的每条关系都必须写清 source、target、cardinality，正反两个名字都要读得通，例如「项目 → 回款约定（1:N）」和「回款约定 → 所属项目」。
5. **一个概念一个名字。** 合并同义词，拆开同名异义。例如「CRM 分类」和「项目类型」是两个字段；「销售人员」就是 `crmOwner`，不要再建 `salesOwner` 属性。单位也要对齐：Excel 导入固定 8 小时一天，项目人天按项目自己的每人天小时数。每个数值属性都要在元数据中声明量纲 `unit`（元、人天、小时、天、月、%、百分点、人、个，或无量纲），按实际含义声明，不按名称推断（「每人天小时数」的量纲是小时）。
6. **每个属性都写清来源。** `sourceKind` 区分系统接口、人工维护、派生计算；派生属性的 `source` 就是它的公式，要能让业务方读懂。说不清来源的属性不能上线。
7. **数值做成参数，算法留在代码。** 可调的阈值放进 `OperatingPolicy`，修改走动作并写审计；判定逻辑写在规则代码里，再把公式抄进属性说明。这样“改口径”是改数据，不用发版本。
8. **本体是带版本的工件。** 任何元数据改动都要升版本：删除或改名属性、改类型、改关系方向属于破坏性变更，升主版本；新增属性、对象、动作升次版本；只改说明文字升修订号。同一版本号的内容不能变。
9. **人工把关治理决策。** 范围、口径取舍、破坏性变更、发布，交给用户决定。遇到口径冲突或可以优化的地方，列出选项和推荐，用提问让用户选，不要自行改变业务含义。
10. **不是每次都要全量推理。** 校验和推理有代价。日常查询走对象索引缓存；只有写入、发布、导入时做完整校验。
11. **抽取完不算完。** NeOn-GPT 的经验是：LLM 的初稿必然有语法错误、不一致和结构缺陷，只靠一次生成得不到可用的本体。改完元数据后按「语法 → 一致性 → 结构缺陷」逐级诊断，把报错整理成诊断报告，读懂每一项再修，修完重跑，直到通过（工作流 E）。
12. **每条规则写依据和验收口径，例外表不能为空。** 这是用户定下的硬性要求。依据让规则可追溯，验收口径让实现可证明，例外表逼着人想清楚边界；一条例外都没有，说明边界没有想过，直接判不合格。格式和判定标准见 `references/build-package.md`。
13. **判断是对关系的推断，要带依据，并区分观察到的和推出的。** 情境感知论文的结论：对象和属性大多能直接观察，「现在发生了什么」要靠关系和推理得出。风险等级、健康状态、经营判断、策略信号都是这种判断，讲的是项目与里程碑、回款、人员、阈值之间的关系。所以：每个判定类派生属性（名称以 Level、Status 结尾的派生枚举）都要在同一对象上配一个依据属性（如 `riskLevel` ↔ `riskReasons`），写出触发它的事实和规则；观察到的事实只来自导入和人工维护，推出的事实只能由推导规则或函数产生，不能反过来写回成「观察到的」。lint 会检查判定类属性有没有依据。
14. **区分「是」「否」「不知道」，承认知识是部分的。** 情境理论用「支持」而不是「满足」，就是承认对情境的知识不完整。缺数据时不能当成「否」或「健康」：要么给出明确的取值（「无基线」「无数据」「无目标」），要么在依据里写出缺了什么；没有权限看到的值是「已隐藏」，页面要单独提示，不能显示成「无数据」。每张规则卡的例外表都要回答：输入缺失时规则给什么结果。
15. **每条规则只有一个归属，只有一份实现。** 借鉴 ontology-driven-dev 的规则归属纪律。只依赖一个属性的约束，是属性级；同一对象多个属性或状态的约束，是对象级；跨对象或被多个动作复用的，是跨对象规则；可调的数值放进运营口径参数。归属定下来后，规则只在本体的提交条件或推导规则里实现一次；基础程序需要兜底时，调用同一个判定函数，不另写一份。经验库 L32 就是双写导致的：提交条件和写入逻辑各说各的。
16. **一个动作只改它声明过的对象，跨对象联动要显式声明。** 动作的 `edits` 要列全它实际写入的对象，例如编辑回款约定会同步回款节点，就必须列出 `PaymentNode`。「A 发生后，满足条件就改 B」这类联动要写进需求基线的联动清单，条件用规则表达，不能藏在基础程序里顺手完成。L33 和需求基线第 6 节的「未声明」项，都是联动藏在代码里造成的。

## 工作流程

按任务类型选一个流程。新需求先走工作流 F（需求探索），确认后再进入 A 或 B。凡是改动本体的流程（A、B），最后都要走工作流 E 的诊断循环，并交付下面「交付物」一节列出的全部内容。

### F. 需求探索（改本体之前）

借鉴 ontology-driven-dev 的做法：AI 可以很快，但业务真相由人拍板。用户的反馈（包括一张截图）先变成需求基线中的条目，确认后才进入本体。

1. **定位**：在 `docs/requirements/TSG_PM_需求规格与本体基线.md` 中找到它涉及的对象、行为、规则、联动或报表，写出它回答的能力问题。
2. **分类**：
   - A 类是行业通识，例如合同有编号和金额、日期控件用日期选择。直接给出做法，标注「按通用做法补全，请确认」。
   - B 类取决于本企业的制度、组织或口径，例如是否含税、要不要审批、谁能看到哪些项目、年度回款按什么日期算。必须提问，不能自己假设。
3. **提问格式**：每个 B 类问题都要附上建议，不许只提问不给答案。

   ```text
   问题N：[需要确认的问题]
   AI建议：[明确的建议答案]
   建议理由：[为什么推荐，以及对对象、规则、联动的影响]
   其他选项：
   A. [备选答案及影响]
   B. [备选答案及影响]
   请回复「按建议」、选项字母，或直接说明修改意见。
   ```

   在对话中优先用提问工具，把建议放在第一个选项。
4. **规则归属与联动**：新规则按原则 15 定归属；涉及第二个对象的，按原则 16 写进联动清单，标明触发、条件、结果。
5. **写回基线**：确认的结论写进需求基线，删掉对应的待确认问题。基线还有待确认项时，只能做不受影响的部分。
6. **成批发布**：相关的需求合并成一个构建包、一个版本。界面显示类的小修（不改元数据）不出构建包，只记 PRD 修订记录。

### A. 把业务文档或口径吸收进本体

这是本项目最常见的任务，例如《业务规则与计算口径说明》。按论文的两阶段做法拆开：先抽取，再对齐。

1. **写需求规格**：按 NeOn 方法论，先写清这次构建的目的、范围、需求，再写 5–10 个能力问题，例如「哪些项目预算使用率超过关注线？」「这个商机的投入有多少成了沉没成本？」。这些内容放进构建包的 `scope`。
2. **抽取候选，并标注出处**：逐条列出文档中的概念、字段、关系、规则和参数。每条候选记下出处（文档第几节），格式见下方模板。这一步只是假设空间，不要直接改代码。
3. **与现有本体对齐**：对每条候选，先在现有元数据中找同义项。能复用就复用；需要新建时判断它是对象、属性、关系、枚举值还是参数（原则 3）；检查关系方向（原则 4）。
4. **找冲突和改进点**：对照现有代码的实际行为。文档与代码不一致、文档自身前后矛盾、口径有缺陷时，列成表，给出推荐，交给用户选（原则 9）。
5. **写规则卡与例外表**：每条要落地的规则写成规则卡（规则、依据、验收口径、验证测试、落在哪些本体元素上），再逐条想例外，填进例外表。先写规则卡再写代码，验收口径就是之后要写的测试。规则卡和例外里写到的系统事实（配置值、时区、权限与标记、页面行为）先在代码或配置中找到出处再写，找不到就去查，不凭印象（经验库 L28、L31）。
6. **落地**：参数进 `OperatingPolicy`，判定逻辑进 `rules.py` 或仓储代码，公式写进属性的 `source`，写操作做成带校验条件的动作。
7. **测试**：每条规则卡的验收口径写成测试，测试名填回 `verifiedBy`。测试应当用能力问题来写，例如「把关注线调到 70% 后，75% 的项目出现在风险原因里」。
8. **诊断与修复**：走工作流 E，直到诊断报告通过。
9. **发布**：升版本号，更新 `docs/BUSINESS_RULES.md` 的“本体位置”一列、`docs/ONTOLOGY_ARCHITECTURE.md` 和 PRD。

候选清单模板：

```markdown
| 候选 | 类别（对象/属性/关系/枚举/参数/规则） | 出处 | 对齐结果 | 决定 |
| --- | --- | --- | --- | --- |
| 销售人员 | 属性 | 口径说明 §1 | 等同 Project.crmOwner | 复用，改显示名 |
| 失效 | 枚举值 | 口径说明 §1 | 属于商机状态，不是新类型 | 加入丢单状态参数 |
```

### B. 新增或修改对象、属性、关系、动作

1. 写下这个改动要回答的能力问题，以及它属于哪个对象。
2. 检查是否已有同义项（`grep` 元数据的 `apiName` 和 `displayName`）。
3. 修改 YAML：属性要有 `sourceKind`、`source`；数值属性要有 `unit`；金额（`unit: yuan`）加 `FINANCE` 标记，个人工时加 `PERSONNEL`；关系写清方向和基数。
4. 有写入就配动作：参数、权限、`edits`、`writeback`、`submissionCriteria`。人工维护的属性如果没有任何动作能修改它，lint 会提示。导入后必须补充的属性或关联，在对象类型的 `maintenanceRequirements` 中声明（并登记推导规则 `maintenanceStatus`），不要在代码里判断「是否维护完整」。
5. 加载器或规则：`rules.py` 中注册 datasource、derivation、handler、criterion、function。派生属性由推导规则（derivation）计算：在对象类型的 `derivations` 中登记，属性的 `derivedFrom` 指向它，计算代码放在 `ontology/derivations/`；**分析计算不放进基础程序**（基础程序只维护主数据和关键字段）。新表要加入 `db.py` 的 `OBJECT_DATASETS`，否则对象索引不会失效。
6. 升版本，写构建包（规则卡与例外表），跑测试，走工作流 E；必要时在前端的函数结果视图中加对应展示。

### C. 用本体回答或核验运营问题

两篇论文的做法合在一起：先按「目标 → 焦点 → 背景」定位情境（情境感知论文），再生成答案并拿本体核验（双回路）。

1. **写清目标**：把问题改写成一个可以判定的问题，例如「SEY101 现在是否需要推动验收回款？」。目标决定哪些对象和关系是相关的，没有目标就无法判断「相关」。
2. **定焦点对象**：先找出问题直接提到的对象（项目、员工、客户），再沿关系推出其他相关对象（里程碑、回款节点、工时、成员），不要一开始就拉全量数据。
3. **取背景**：列出推理要用到的背景及其当前值，例如运营口径参数（预算关注线 80%）、工作日历、年度计划。背景变了，结论可能就变了。
4. **翻译成本体调用**：用对象集或函数（对象类型、过滤条件、沿关系检索、聚合），不要只靠文本检索或记忆。取回结果时同时取回口径：属性的 `source` 和用到的参数值。
5. **推断并分清三类事实**：观察到的（导入、人工维护）、推出的（推导规则、函数）、不知道的（缺数据、无权限）。不知道的不能当成「否」。
6. **回答给出结论、数据和依据**：依据要能追溯到对象编号、规则和参数。如果问题里的说法与本体结论不一致，明确标出「与系统口径不符」，并说明是哪条规则、在什么条件下成立；有数据缺失时说明结论的可信程度。
7. **推断出的新事实只作建议**：例如「这个商机应当判为丢单」，要由用户通过动作确认后才写入。

### D. 评审本体变更

逐项检查，并在评审意见中写明结论：

- 范围：每个新增概念都对应一个能力问题吗？
- 类型与实例：有没有把取值当成类型？
- 关系：方向、基数、正反名称都正确吗？有没有两条关系表达同一件事？
- 命名：是否与已有概念重复？显示名是否与业务口径文档一致？
- 来源：每个属性都有 `sourceKind` 和可读的 `source` 吗？派生属性的公式写全了吗？
- 安全：金额和人员数据是否加了标记？动作权限是否最小？
- 写入：人工维护的属性是否有动作或维护接口，且有校验条件和审计？
- 版本：版本号是否按破坏性程度升级？版本差异页的结果与预期一致吗？
- 判定与依据：新增的等级、状态类派生属性有没有依据属性？依据能否追溯到观察到的事实和规则？
- 未知与部分性：输入缺失、无权限时，结果是明确的「无数据 / 无基线」或带提示，而不是「健康」「达标」或 0 吗？
- 证据：测试是否覆盖了新口径？诊断报告是否通过？
- 构建包：每条规则都有依据和验收口径吗？例外表是否非空，例外是否真的来自边界思考而不是凑数？

### E. 校验—诊断—修复循环

参照 NeOn-GPT 的三道闸：每道闸的报错整理成诊断报告，读懂后修复，再重新诊断。

1. **运行诊断**（在 `backend` 目录）：

   ```bash
   .venv/bin/python ../.claude/skills/tsg-ontology/scripts/diagnose_ontology.py --database <数据库文件> --build ../docs/ontology-builds/<构建包>.yaml --require-build
   ```

   阶段依次是：1 语法（YAML 与元数据模式）、2 一致性（引用、连接键与基数、版本登记；带 `--database` 时还检查数据：主键唯一、枚举取值、值类型、悬空引用、运营口径参数自洽）、3 结构缺陷（lint）、4 构建包（规则卡与例外表）。前一阶段有严重问题时，后面的阶段跳过。报告写在仓库的 `.ontology-diagnostics/latest.md`，并自动与上一轮比较。
2. **读报告，不要只看结论**：每一项都写了问题、为什么重要、修复建议和样例。修之前先回答：它为什么会出现？是数据问题、建模问题，还是业务上的预期？
3. **按顺序修**：先严重，再重要；一轮只修一个阶段的问题。次要问题只在确认不会破坏一致性时处理——NeOn-GPT 的实验显示，模型修次要缺陷时最容易把本体改坏。业务上的预期（例如未建档代码导致的悬空引用）不要硬修，在说明里声明原因。
4. **重新诊断**：看报告里的「已解决、新增、仍存在」。新增的问题多半是上一轮修复引入的，优先处理。
5. **记经验**：每轮结束把新学到的模式追加到 `references/lessons.md`。同一模式第二次出现，就升级为诊断或 lint 检查，或写进本技能的原则。
6. **知道何时停**：报告通过（没有严重和重要问题）即可结束。同一问题连续 3 轮仍未解决，报告会标出来，这时停止自动修复，把该项和你的分析交给用户决定。

## 交付物

每次建立或修改本体，交付以下全部内容，缺一项都不算完成：

0. 需求基线的更新：涉及的对象、行为、规则归属、联动或报表已写进 `docs/requirements/TSG_PM_需求规格与本体基线.md`，没有遗留与本次相关的待确认项。
1. 元数据改动，并按原则 8 升版本号。
2. 构建包 `docs/ontology-builds/<日期>-<主题>.yaml`：能力问题、规则卡（依据、验收口径、验证测试），以及**非空的例外表**。
3. 覆盖每条验收口径的测试，全部通过。
4. 通过的诊断报告（带 `--database`、`--build`、`--require-build`）。
5. 经验库的更新，以及相关文档（口径文档、本体架构、PRD）的同步修改。

## 质量检查脚本

- `scripts/diagnose_ontology.py`：四阶段诊断，输出诊断报告，见工作流 E。
- `scripts/lint_ontology.py`：诊断的第 3 阶段，也可以单独运行。它加载真实元数据，检查编译器不管的质量问题：缺少口径说明的派生属性、没有依据属性的判定类派生属性、没有写入动作的人工属性、未加标记的金额属性、看起来像实例的类型名、重复或反向的关系、孤立对象、没有校验条件的高风险动作等。在 `backend` 目录运行：

```bash
.venv/bin/python ../.claude/skills/tsg-ontology/scripts/lint_ontology.py
```

加 `--strict` 时，有警告就返回非零退出码，可以放进 CI。警告不一定都要修：有些是设计如此（例如运营口径参数本来就不与其他对象关联），这时在评审意见里说明原因即可。

## 汇报时的证据纪律

论文作者把可验证的结论和项目素材严格分开，小样本结果只当描述性证据。照此办理：

- 说「已验证」时，给出测试名或命令输出；没有跑过的，明确说没有验证。
- 数字结论注明口径和参数，例如「按预算关注线 80%」。
- 演示数据得出的结论，注明是演示数据。
