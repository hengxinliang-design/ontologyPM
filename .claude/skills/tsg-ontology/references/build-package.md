# 本体构建包：规则卡与例外表

每次建立或修改本体，都要交付一个构建包，放在 `docs/ontology-builds/<日期>-<主题>.yaml`。诊断脚本用 `--build` 读取它，`--require-build` 保证不交构建包的构建直接不合格。

**硬性要求（用户规定）：每条规则必须写依据和验收口径；必须产出例外表，一条例外都没有直接判不合格。**

## 为什么要这样做

- **依据**让每条规则可以追溯：口径有争议时，能回到原始文档、用户决定或法规条款判断对错，而不是凭记忆。
- **验收口径**把“规则已经实现”变成可以观察和重复的事实：输入什么、期望看到什么。最好再指向一个自动化测试。
- **例外表**逼着人想清楚边界。没有例外的规则通常不是真的没有例外，而是没有想过。第一份构建包在写例外表时就发现了两条写入路径校验不一致，这正是例外表的价值。

## 模板

```yaml
kind: OntologyBuild
topic: 一句话说明这次构建做了什么
ontologyVersion: 2.0.2          # 必须等于本次发布的本体版本
date: 2026-10-26
scope:                           # 能力问题：这次构建要让本体能回答什么
  - 能力问题：……？

rules:
  - id: R1                       # 构建包内唯一
    statement: 规则本身，一句话。
    basis: 依据：来源文档和章节、用户决定（日期）、法规条款或已有代码行为。
    acceptance: 验收口径：可观察的通过条件，写明输入和期望结果。
    verifiedBy: [test_function_name]   # 真实存在的测试函数名
    ontology: [updateOperatingPolicy, OperatingPolicy.budgetAttentionPercent]   # 规则落在哪些本体元素上

exceptions:                      # 不能为空
  - rule: R1                     # 引用上面的规则编号
    case: 例外情形：什么情况下规则不按字面执行。
    handling: 处理方式：这时系统怎么做。
    basis: 依据：为什么这样处理。
```

`ontology` 可以写对象类型、`对象.属性`、`对象.关系`（正反名称都可以）、动作、函数、值类型或校验规则名。

### 设计稿与发布稿

`stage` 取 `design` 或 `release`（缺省为发布稿）。

- **设计稿**（`stage: design`）：在实施之前评审本体设计。`ontologyVersion` 写计划发布的版本，必须高于当前版本。`ontology` 和 `verifiedBy` 可以引用尚未实现的元素和测试，诊断记为次要（计划中）。**依据、验收口径和非空例外表的要求与发布稿完全相同。**
- **发布稿**：实施完成时交付。`ontologyVersion` 必须等于当前版本，引用的元素和测试都必须真实存在。

实施时把设计稿复制为发布稿，补齐 `verifiedBy`，去掉 `stage: design`，再跑诊断。

### 被取代的构建包

构建包记录的是它交付时的版本。之后本体再升版本，旧构建包的版本检查就会失败。这时给旧构建包加 `supersededBy: <同目录下取代它的构建包文件名>`：诊断跳过它的版本检查，它引用的、已被后续构建移除的元素和测试降为次要。取代它的构建包必须存在，版本也不能更低（BLD-SUPERSEDED）。依据、验收口径和例外表的要求不变。设计稿在发布稿交付后同样标注 `supersededBy`。

## 诊断脚本如何判定

| 检查 | 级别 | 说明 |
| --- | --- | --- |
| 构建包缺失（`--require-build` 时） | 严重 | 没有规则卡和例外表的构建一律不合格 |
| 例外表为空 | 严重 | 规定：一条例外都没有直接判不合格 |
| 规则缺依据 | 严重 | `basis` 为空 |
| 规则缺验收口径 | 严重 | `acceptance` 为空 |
| 规则编号重复、缺 `statement`、文件格式不对 | 严重 | 构建包本身无效 |
| 没有 `verifiedBy`，或引用的测试不存在 | 重要 | 验收口径缺少可重复执行的证据 |
| `ontology` 引用的元素不存在 | 重要 | 规则与本体脱节 |
| 例外引用了不存在的规则，或缺少情形、处理、依据 | 重要 | 例外表本身不完整 |
| 版本号与当前本体不一致 | 重要 | 构建包过期；已被后续构建取代的写 `supersededBy` |
| `supersededBy` 指向的构建包不存在或版本更低 | 重要 | 历史构建包无法追溯 |
| 某条规则没有登记任何例外 | 提示 | 报告中列出，提醒确认是真的没有例外 |

## 怎样想出例外

逐条规则过一遍下面的清单。每一项都是一个可能的例外来源：

1. **边界值**：恰好等于阈值时归哪一档？0、空、100% 怎么处理？
2. **数据缺失**：来源字段为空、日期缺失、CRM 没有记录时怎么办？
3. **多个来源冲突**：合同与商机、人工结论与 CRM 状态不一致时谁优先？
4. **两条写入路径**：系统设置页、维护接口和本体动作的校验是否一致？
5. **组合修改**：多个参数需要同时调整时，中间状态是否会被误拒？
6. **时间与跨期**：跨月、跨年、节假日、历史数据迁移时规则是否还成立？
7. **权限差异**：没有金额权限的用户看到什么？
8. **演示数据与生产数据**：演示数据中的异常是否代表真实情况？
9. **规范化**：大小写、空格、同义词、单位（小时与人天）如何统一？
10. **业务方可能提出的变更**：哪些要求是刻意不支持的，为什么？
11. **「否」与「不知道」**：输入缺失或没有权限时，结果是「否」「未知」还是「已隐藏」？三者有没有被混成同一个值？
12. **情境的边界**：判断用到了哪些对象和关系？有没有相关的对象没被纳入（例如只看合同、不看商机；只看本月、不看跨月的工时）？
