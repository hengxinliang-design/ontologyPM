# 四篇论文的要点与本项目的对应做法

本文件记录 SKILL.md 中原则的出处。需要向用户解释某条做法的依据，或者设计新的本体构建流程时再读。

## 论文一：把 LLM 作为外部记忆、校验与规划层来自动构建本体

Salovsky & Gorshkova, *Automatic Ontology Construction Using LLMs as an External Layer of Memory, Verification, and Planning for Hybrid Intelligent Systems*, arXiv:2604.20795。

### 核心主张

- LLM 不是知识库，而是外部记忆之上的解释、生成和编排层。外部记忆由本体图（RDF/OWL）承担，向量检索只负责召回文本片段。
- 双重记忆：图负责语义、约束和可解释性，向量库负责召回和“文本残留”。一次查询的上下文由四部分融合：向量检索、图检索、工具调用、用户或会话记忆。
- 本体让系统从“检索一段上下文”变成“更新一个可解释的世界模型”，带来长期记忆、可解释推理、矛盾控制和更稳的规划。

### 本体构建流水线（Ontology Builder）

| 阶段 | 要点 | 本项目对应 |
| --- | --- | --- |
| 1 摄取与切分 | 从一开始就保留溯源：哪个来源、哪一段产生了实体或关系 | 属性的 `source`；候选清单的“出处”列 |
| 2 实体识别与定型 | 大部分错误发生在这里：类不全、类型与实例混淆、别名歧义、domain/range 错误。输出只是假设空间 | 工作流 A 第 2 步只列候选，不改代码 |
| 3 关系抽取 | 以目标模式为锚点能显著提升一致性 | 对齐到已有对象与关系 |
| 4 规范化与对齐 | 稳定标识、合并同义、拆分同名、去重；处理单位、过时版本、同一对象不同标识；保留历史和替代解释 | 原则 5；版本登记 |
| 5 三元组构建 | 关系从隐含在文本里变成一等对象 | 关系类型、对象属性 |
| 6 校验 | 结构校验（SHACL：必填、基数、取值类型）与逻辑校验（OWL 推理：一致性、层级） | 编译器与 Pydantic；动作校验条件；lint 脚本 |
| 7 写成 TTL 并发布 | 可序列化、可版本化的中间工件，支持 CI 校验、差异比较、溯源和复现 | YAML 元数据与版本差异 |
| 反馈回路 | 回答中的新事实成为候选增量；校验不过的只留在日志，不进入可信图 | 原则 1；工作流 C 第 4 步 |

### 双回路与规划

- 生成回路给出答案，本体与校验器回路给出判定（支持或矛盾），并附上规则及其适用条件。论文的法规案例中，纯 LLM 答案被判为矛盾，基于本体的答案依据具体规则成立。
- 规划按“提议 → 符号校验 → 修正 → 执行”循环。汉诺塔实验中，本体增强在中等难度（3 盘、5 盘）提升成功率，简单与过难时没有差别。作者明确说明样本和协议未公开，只算描述性证据。

### 局限与建议

- 自动构建不等于无误：存在模式漂移、幻觉关系、复用困难，需要多维度评估。
- 必须持续规范化，否则图会变成“精致的混乱”。
- 推理和校验有延迟，不是每个查询都该触发完整推理。
- 人工参与不能省：至少在模式治理、评估标准和发布管理上。
- 后续方向：时间维度与版本化本体、单位管理、三元组置信度。

## 论文二：面向企业知识图谱的 LLM 本体构建（OntoEKG）

Oyewale & Soru, *LLM-Driven Ontology Construction for Enterprise Knowledge Graphs*, arXiv:2602.01276。

### 方法

1. 用 Pydantic 定义严格的数据模型，强制 LLM 输出合法 JSON：类、属性、描述、domain、range。
2. 抽取模块：专门的系统提示词，只抽取类和属性，并且只围绕给定的模式。
3. 蕴含模块：另一个 LLM 逐一判断类之间的继承关系，依据是类的描述。
4. 用 rdflib 序列化为 owl:Class 与 owl:ObjectProperty 的 Turtle 文件。

### 结果

- 精确匹配的 F1 很低（数据领域 0.10，金融领域 0），模糊匹配（嵌入相似度阈值约 0.94）后数据领域 0.72、物流 0.43、金融 0.12。
- 金融领域差，原因是对文本的理解不同：哪些术语该进本体、哪些属于上下文之外。

### 失败模式（对应 SKILL.md 原则 2–4）

- 范围：模型无法自主决定合适的建模范围，需要明确给出边界。
- 抽象层级：模型会提出个体而不是类，因为没有声明目标抽象层级。
- 层级推理：会弄反继承方向；会采用宽松的包含定义，例如把两个类互相声明为子类（等于宣布等价）；会引入含义不清的属性，例如 isTypeOf，分不清 rdf:type 和 subClassOf。

### 后续方向

- 保留实体来源信息（溯源）。
- 渐进式构建：把已有本体和新文本一起交给模型，保证跨文档一致。本项目工作流 A 第 3 步“与现有本体对齐”就是这个做法。
- 评测要区分 TBox（模式）和 ABox（实例），并且端到端评估整条流水线。

## 论文三：NeOn-GPT——按方法论组织的 LLM 本体学习流水线

Fathallah, Das, De Giorgis, Poltronieri, Haase, Kovriguina, *NeOn-GPT: A Large Language Model-Powered Pipeline for Ontology Learning*。代码：github.com/andreamust/NEON-GPT。

### 方法

1. **需求规格先行（NeOn 方法论）**：领域描述、本体目的、范围、需求，以及能力问题。用角色扮演（「资深知识工程师」）和逐步推理提示。
2. **从能力问题抽取实体与关系**，先得到主谓宾三元组的概念模型，再实现为 Turtle；随后补充逆、自反、传递、对称、函数性等属性特征，补充说明文字、标签、版本等元数据，最后用真实实例填充。
3. **校验—修复三道闸**，每道闸的报错原样拼进提示，让模型修复后重检：
   - 语法：RDFLib 解析，语法错误交给模型修复；
   - 一致性：HermiT 推理机找出不一致，报错交给模型修复；
   - 结构缺陷：OOPS! 扫描常见缺陷（如循环公理、缺少不相交声明），按严重、重要、次要分级，交给模型修复。
4. **嵌入工作流平台**（metaphactory 的工作流本体）：每一步有说明、模板和产物，上一步的输出合格才能进入下一步。原因是 LLM 不擅长程序性任务，会跳步、产生零散或幻觉的结果。

### 结果与教训

- 与零样本提示、照着建模指南提示相比，流水线产出的本体层级更深、没有语法错误和冗余术语，并且逻辑一致。
- 模型能修好严重和重要的缺陷，但**修不好次要缺陷，而且修次要缺陷时容易破坏一致性**。
- 与人工金标准（斯坦福葡萄酒本体）相比：类只有一半，属性更多，但公理少得多（387 对 911），层级更浅（L0–L2 对 L0–L3），个体少。
- 类表达几乎只有包含关系，缺少合取、析取；属性限制几乎只有 HasValue，缺少基数、存在、全称限制，所以推理能推出的东西很少。
- 结论：LLM 适合做半自动流水线中的初稿生成，由人补充表达力；需要和工作流工具紧密结合。

### 本项目对应做法

| NeOn-GPT | 本项目 |
| --- | --- |
| 需求规格与能力问题 | 工作流 A 第 1 步；构建包的 `scope` |
| RDFLib 语法检查 | 诊断阶段 1：YAML 解析与元数据模式 |
| HermiT 一致性检查 | 诊断阶段 2：引用、连接键与基数、版本登记，以及带 `--database` 的数据一致性（主键、枚举、类型、悬空、参数自洽） |
| OOPS! 分级缺陷扫描 | 诊断阶段 3：lint 结构缺陷，按严重、重要、次要分级 |
| 报错拼进提示让模型修复 | 诊断报告即修复输入：每项给出问题、为什么重要、修复建议 |
| 次要缺陷修复会破坏一致性 | 修复顺序为严重、重要；次要只在确认安全时处理，处理后必须重跑全部阶段 |
| 公理和限制太少 | 评审时专门检查约束是否充分：基数、必填、取值范围、提交条件 |
| 嵌入工作流 | 诊断脚本的阶段闸门、构建包、`--require-build` |

## 论文四：基于本体的情境感知（Situation Theory Ontology）

Kokar, Matheus & Baclawski, *Ontology-based situation awareness*, Information Fusion 10 (2009) 83–98。

### 核心主张

- **情境是关系，不是对象清单。** 只知道每个球员在哪，看不懂比赛；知道规则、能推出「谁在进攻、谁在防守」，才算感知到情境。对象和属性大多可以直接观察，关系大多要推断。感知 = 观察到的数据 + 背景知识 + 推理能力，用来回答「现在发生了什么」。
- **用形式化本体统一概念。** 作者把 Barwise 的情境理论写成 OWL 本体（STO），让不同系统对「情境」有同一套可计算的词汇；OWL 表达不了的部分（属性复合、带变量的连接）用规则补上。他们承认这只是「对应」，不是严格等价。

### 关键概念

| 概念 | 含义 | 要点 |
| --- | --- | --- |
| 信息单元（infon） | 〈关系, 对象1…对象n, 极性〉 | 极性 1 表示关系成立，0 表示明确不成立；「不知道」是第三种状态，不能写成 0 |
| 支持（supports）与推出（derives） | 情境「支持」某些信息单元；信息单元之间按规则「推出」 | 「支持」弱于模型论的「满足」：承认对情境的知识是部分的 |
| 观察到的与推出的信息单元 | 观察到的来自传感器或其他来源，必须显式给出；推出的由规则从观察到的（或其他推出的）得到 | 例子：由位置和速度推出「靠近」「朝向」，再推出「追逐」，再结合观察到的「不友好」推出「威胁」 |
| 情境类型与「蕴含」（involves） | 情境按类型分类；类型之间的约束 S0 ⇒ S1 是领域规律 | 同一情境内的蕴含就是子类关系（OWL 子类推理）；跨情境的蕴含要用规则 |
| 话语情境、焦点情境、资源情境 | 提问（目标）所在的情境、问题所指的那部分世界、推理时借用的背景情境 | 目标决定哪些对象「相关」；先给出焦点对象，再推出其他相关对象 |
| 参数与锚定 | 关系的每个位置有类型限制，参数锚定到具体对象 | 关系参数必须类型相容 |
| 属性的量纲（DIM） | 值带单位，如 [m/s]、[km] | 情境理论原本没有，作者专门加上，因为没有量纲就无法比较和计算 |
| 规则的一般性 | 针对 Rex 写的子类规则只对 Rex 有效；带变量的规则（near ∧ inDirectionOf → chases）对任意对象有效 | 规则按类型写，不按个例写 |
| 查询与交流 | 查询的答案包括推出的事实；情境可以作为对象传给另一方，之后只发增量并引用同一个情境 | 双方必须共享同一套本体 |

### 局限

- 需要 OWL Full（类同时是实例），推理代价高；很多规则要退回到规则语言。
- 例子很小（狗、猫、老鼠），没有评估实际系统的规模和效果，结论只能当作建模原则参考。

### 本项目对应做法

| 情境理论 | 本项目 |
| --- | --- |
| 观察到的信息单元 | `sourceKind: system / manual` 的属性：导入和人工维护的数据 |
| 推出的信息单元 | `sourceKind: derived` 的属性，只能由推导规则（`derivations`）或函数计算 |
| 推理的依据链 | 判定类属性配套的依据属性（`riskLevel` ↔ `riskReasons`、`healthStatus` ↔ `healthReasons`）；lint 检查判定类属性缺少依据 |
| 极性与「不知道」 | 明确的「无基线 / 无数据 / 无目标」取值；脱敏后的值是「已隐藏」，页面单独提示，不能显示成「无数据」 |
| 部分知识 | 推导结果附「数据提示」，写出缺了什么（例如「剩余人天估算缺失，按预算人天估算」） |
| 情境类型与分类规则 | 风险等级、健康状态、资源健康、策略信号都是情境类型；分类规则写成规则卡，按严重程度排序 |
| 话语 / 焦点 / 资源情境 | 工作流 C：先写清问题（目标），再定焦点对象，沿关系找相关对象，再取背景（运营口径参数、工作日历、年度计划）的当前值 |
| 规则按类型写 | 阈值放运营口径参数，规则对所有项目生效；只对某个项目成立的特例写进例外表 |
| 量纲 | 元数据中每个数值属性声明 `unit`（4.1.0）；lint 按量纲识别金额，页面按量纲加单位 |
| 交流情境 | 页面函数返回 `redacted_markings` 等元信息；把情境做成可引用的对象是后续方向（见下） |

### 对现有本体的观察（供决策，尚未实施）

1. **策略信号和经营判断还不是对象。** 它们是函数的即时输出，没有历史、不能被查询或关联到管理干预。按情境理论，可以把「情境」建成对象类型：情境类型（如「推动验收回款」）、相关对象（项目、员工）、期间、支持它的信息单元（观察到的与推出的分开，带极性）。这样能回答「这个预警出现过几次」「处理后是否消失」，也能在管理干预里引用。
2. **风险等级没有「未知」。** 项目类型未设置、里程碑未制定时，风险等级是「关注」，原因写在依据里。这把「数据不全」和「真的有风险」放在了同一档。是否增加「数据不足」取值，要由用户决定。
3. **属性没有量纲。**（已实施，本体 4.1.0）每个数值属性声明 `unit`，lint 与页面格式化改用量纲判断。

## 四篇论文共同指向的做法

1. 先模式、后实例；先抽取、后蕴含；分阶段，每阶段可检查。
2. 结构化输出加严格模式，是保证可用性的第一道关。
3. 溯源从第一步开始记录。
4. 校验分结构和逻辑两层，校验不过的不进入可信本体。
5. 本体作为版本化工件管理，用差异比较和 CI 守住质量。
6. 人工把关范围和发布。
7. 如实汇报证据强度，小样本只作描述。
8. 抽取完不算完：语法、一致性、结构缺陷逐级检查，把报错整理成诊断报告驱动修复，循环到通过为止。
9. 判断是对关系的推断：每个判定都能追溯到它所依据的观察事实和规则，观察到的与推出的分开。
10. 承认知识是部分的：区分「是」「否」「不知道」，缺数据时说出缺了什么，而不是给出一个看似确定的结论。
