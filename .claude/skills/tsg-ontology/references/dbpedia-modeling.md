# DBpedia：后续企业建模的参考方法

指引版本 1.0.0；研究核对日 2026-10-30。配合 external-vocabularies.md 使用。本文是建模指导，不启用数据接入、不发布运行时本体、不批准任何外部身份链接。

## 先区分三个层次

DBpedia 是从 Wikipedia 等来源组织结构化知识的项目，包含本体、抽取映射和实例数据。它不是业务流程或权限引擎。

| 层次 | 命名空间 | 建模时如何使用 |
| --- | --- | --- |
| dbo：类和规范化属性 | http://dbpedia.org/ontology/ | 查找跨领域概念及属性候选；核对具体词条定义和固定版本 |
| dbp：原始信息框属性 | http://dbpedia.org/property/ | 仅作来源字段和抽取线索；同名属性不保证统一类型、单位或语义 |
| dbr：实例资源 | http://dbpedia.org/resource/ | 公共实体链接候选；不是类定义，也不是内部主键 |

例如 dbo:Person 是类，dbr:Berlin 是实例。dbo:Organisation 的拼写不同于 schema:Organization，不得靠字符串相似自动映射。HTTP 命名空间不能因浏览器跳转 HTTPS 就改写。不同语言版本、重定向和消歧义页面需逐项核验，不能凭标签合并。

## 最值得学习的方法：把来源映射到统一语义

DBpedia 的 mapping-based extraction 将不同信息框及字段映射到共享本体，并处理类型与值规范化。对本项目的借鉴是：CRM、工时和人工计划的原始字段留在来源层；对象类型、关系和计算口径集中在内部语义层。不要把每个系统的表、字段或具体记录原样变成本体类。

后续每次建模按下面顺序处理：

1. 写能力问题，例如“同一客户在多个来源中的项目如何归集”；先在需求基线和内部本体查找已有对象、字段和唯一标识。
2. 分开登记类、属性、关系与实例。按业务含义定义，避免复制百科分类树。
3. 查 dbo 以及 Schema.org、FOAF、Dublin Core 的相关定义。DBpedia 适合公共人物、组织、地点及背景知识；前三者仍按既有指引选择，不规定全局优先次序。
4. 写来源字段→内部元素映射：来源系统/表/字段、内部模型版本、转换、单位、基数、空值、时间范围和证据。外部语义映射另行登记，不能代替这份数据映射。
5. 将外部类候选与内部类比较：定义、上下位关系、domain/range、生命周期。没有匹配时保留内部定义；项目状态、回款约定、风险判定、权限和动作不强行套用百科语义。
6. 对候选做正例、反例、缺失和冲突验收；需要实现时走原 Skill 的需求基线、规则卡、非空例外表、版本和诊断流程。

## 类型对齐与实体链接必须分开

类型候选：内部“法人客户”可参考 dbo:Organisation，但公共组织包含更多类别，候选关系通常是较宽参考，不能自动宣告等价。

实例候选：内部某客户可能对应某个 dbr 资源。只有名称相同不够，需核对法人主体、官方域名、地点、母子公司关系及有效时间，并保存证据与审核结论。公共实体链接不改变内部 ID，不将分公司、集团、品牌合成一条记录。禁止自动生成 owl:sameAs，禁止沿外部 sameAs 链自动合并内部对象。

示例（概念说明，非当前模型路径或已批准映射）：

```json
{
  "kind": "entity-link-candidate",
  "internalId": "example-customer-001",
  "externalUri": "http://dbpedia.org/resource/Example_Company",
  "status": "candidate",
  "evidence": [],
  "decision": "示意 URI 未验证，不得导入或据此合并身份"
}
```

真实登记还必须满足 external-vocabularies.md 的来源和审核字段。例中 URI 为占位示意，并不声明资源存在。

## 外部事实的使用边界

公共知识只能提供背景补充，不能覆盖 CRM 的合同主体、内部客户关系、财务事实和运营状态。存储时区分外部观察、内部观察和推导，保留原始值、规范化值、来源资源、数据集、语言、版本、抽取/检索时间、有效时间（未知就注明未知）、转换规则与证据。检索时间不能冒充事实发生时间。

缺失三元组表示未知，不表示否；多值、过期信息和冲突保留为候选，不能随机选一条当权威。dbo 数据经过映射也不保证完整或正确；domain/range 推断不等于业务校验。公共 SPARQL 可用于探索，业务服务不依赖其实时可用性。查询外部服务前先确认查询不携带内部客户名单或受限字段；批量使用时先核对具体数据集许可和署名要求。

## 来源、版本与验证

DBpedia 本体快照、实例数据集和公共端点加载版本可能不同。不能把文档更新时间、端点响应时间当作数据集版本。正式采用时锁定 Databus artifact 与具体 version、下载文件及 SHA-256，并记录本体版本和抽取配置；无固定版本先停留在研究候选。升级先做映射差异和回归，禁止静默跟随 latest。

规则卡 R-DBP-1：源字段、规范语义、实例身份分离。依据：DBpedia 官方 DBO、Individual Datasets 文档。验收：dbp 字段不自动成为内部属性；dbr 不作为类；同名客户不自动合并。

规则卡 R-DBP-2：外部知识仅作有来源的候选。依据：用户要求的内部权威原则及 Databus 版本方法。验收：无固定数据版本/证据/审核的条目不能成为可信输入；外部事实冲突不覆盖内部事实；端点失败不改变内部业务结果。

| 规则 | 例外情形 | 处理及依据 |
| --- | --- | --- |
| R-DBP-1 | 客户无百科条目 | 保留内部对象，标记未链接；百科覆盖不是客户存在条件 |
| R-DBP-1 | 同名组织或集团/子公司混淆 | 暂停链接，补法人和时间证据；名称不证明身份 |
| R-DBP-2 | 外部成立日期与内部记录冲突 | 并列保存来源并人工审核；外部不覆盖内部 |
| R-DBP-2 | 缺字段、消歧义页、重定向或端点不可用 | 记未知/待核验，使用已批准快照或跳过补充；不推断不存在 |

本次仅验证指引文件和示例语法，不声称已经实现上述适配器或数据验收。
