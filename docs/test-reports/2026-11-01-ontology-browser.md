## 1. 范围与方法

**接口测试**：`backend/scripts/ontology_browser_check.py`（可重复运行，逐条结果见 [ontology-browser-cases.md](ontology-browser-cases.md)）。

- 阶段 A：本地演示服务器，管理员身份。写操作一律用预检（validateOnly）；唯一的真实执行对象是已锁定的里程碑、已到账回款、已关闭干预和已关联约定，它们必须被拒绝。执行后核对数据没有变化（Z10）。
- 阶段 B：在进程内启动应用并开启登录，用五类账号测试：管理员、PMO、分析人员、项目经理刘浪（本人项目 TPL149、WDR101），以及一个只有「项目管理（只读）」和「本体浏览器」菜单的分析人员（没有 FINANCE、PERSONNEL 安全标记）。
- 判定：每个用例写明预期状态码，以及需要时的响应内容检查；任何 500 都算未通过。
- 第一轮有 19 个未通过，其中 6 个是用例本身写错（static 对象集字段应为 `objects`、资源测算月数范围是 1–6、客户端无法发送 inf 数字、两条检查写法不准、一次 500 之后连接复用被重置），已修正后重跑。

**界面测试**：内置浏览器，桌面宽度和 375px 手机宽度，覆盖五个页签、14 类对象浏览、搜索、分页、详情、动作表单（必填、日期、枚举、预检、锁定）、对象集 JSON 手动编辑、版本差异、审计筛选和控制台错误。

## 3. 发现的问题（按严重程度）

### 高：服务器错误或写入错误的业务数据

**F1 极大数字让任何金额、小数参数返回 500**（P03）
- 步骤：对 `createPaymentTerm` 预检，`plannedAmount` 填 `"1e309"`；`configureProject` 的 `hoursPerPersonDay` 填同样的值也会出错。
- 预期：422，提示数字超出范围。
- 实际：500。`runtime.py` 的 `_coerce` 执行 `number.quantize(Decimal("0.01"))` 时抛出 `decimal.InvalidOperation`，没有被捕获。所有 money、decimal、percent 参数都走这条路径。
- 建议：捕获 `InvalidOperation`，并给金额设定上限（例如不超过 1e12）。

**F2 筛选条件嵌套过深导致递归溢出，返回 500**（Q30b）
- 步骤：对象集查询中，`where` 用 3000 层 `not` 嵌套。
- 预期：422。对象集已有 12 层上限，条件也应有上限。
- 实际：500（Python 递归溢出）；500 层时仍正常返回。
- 建议：在 `objectsets.py` 的 `compile_where` 里计数，沿用 `MAX_DEPTH` 或单独设一个上限。

**F3 确认到账可以填未来日期，未来回款计入该年经营收入**（P56）
- 步骤：对未到账节点执行「确认回款到账」，`actualDate` 填 `2099-01-01`。
- 预期：拒绝，到账日期不能晚于今天。
- 实际：执行成功；部门经营复盘 2099 年的经营收入显示 1,000.00。
- 建议：给 `confirmPaymentReceived` 加提交条件「到账日期不晚于今天」，与「录入经营成本」不能录未来月份的规则一致。

**F4 每人天小时数可以设为 0 或 25**（P35、P36）
- 步骤：「设置项目」把 `hoursPerPersonDay` 设为 0 或 25。
- 预期：拒绝，取值应大于 0 且不超过 24（或更窄的合理区间）。
- 实际：执行成功。设为 0 后，该项目所有已填报人天都显示 0.00：页面不报错，但数字全部失真。
- 建议：加提交条件 0 < 每人天小时数 ≤ 24，范围请业务确认。

**F5 预算人天可以为负数**（P34）
- 步骤：「设置项目」把系统实施项目的 `plannedPersonDays` 设为 -10。
- 预期：拒绝。
- 实际：执行成功；项目预算人天显示 -10.00，预算使用率变为空，而「填写初始预算人天」这条维护要求仍判为已满足。
- 建议：系统实施和 TSnT365 的预算人天必须大于 0。

### 中：校验不一致或会误导用户

**F6 只有空格的名称：预检通过，但执行结果不一致**（P13）
- 步骤：在「新建里程碑」「发起管理干预」「新建回款约定」中，名称或事项只填空格。
- 实际：
  - 三个动作的预检都通过，界面显示「预检通过，可以提交。」；
  - 执行后，里程碑和干预会被创建，名称是空字符串；
  - 回款约定在执行时被拒绝，提示是英文的「payment term name is required」。
- 原因：必填检查在去空格之前进行。
- 建议：先去空格，再判断必填；统一使用中文提示。

**F7 锁定的动作仍能点「提交」**
- 实际：已完成里程碑的「编辑里程碑」表单列出「✕ 里程碑已确认完成，已锁定」，但「提交」按钮仍可点击，提交后服务端拒绝。被拒绝的原因以普通黑色文字显示，没有错误样式。
- 建议：提交条件不满足时禁用「提交」，拒绝原因用错误样式显示。

**F8 PM Assistant 悬浮按钮遮挡页面内容**
- 实际：1024×768 下，按钮正好盖住动作表单右下角的「预检」「提交」，以及对象列表最后一行的「计划完成」日期。
- 建议：给主内容区底部留出按钮高度的空白，或把按钮在内容区内收起。

## 4. 已确认符合设计（不是缺陷）

- 对文本属性用 `gt` 比较是按字典序（Q24）。
- 按「里程碑」筛选动作审计时，包含以项目为目标的「新建里程碑」记录，因为这类动作创建了里程碑（G02）。
- 资源测算只接受 1–6 个月（F15 用例按此修正）。
- 只有一个版本时，「版本差异」显示提示「目前只有一个版本……」，不报错。
- 内部代码 TSG999 不是项目（D12 用例返回 404）；它的成本对象沿「项目」关系遍历返回空列表（K09）。

## 5. 通过的重点

**安全与数据范围（阶段 B，33 个用例全部通过）**
- 未登录或伪造令牌访问任何接口都返回 401。
- 本体浏览器中只有管理员能执行动作（D12）：
  - PMO 在浏览器执行返回 403，经业务渠道执行通过；
  - 分析人员即使走业务渠道也返回 403；
  - 渠道头写成大写的 `BUSINESS` 不会被放行。
- 非管理员不能刷新对象索引。
- 项目经理的数据范围在每一条路径上都成立：
  - 项目列表只有本人的 2 个项目；他人项目详情返回 404；
  - 用 static 对象集直接指定他人项目，返回空；
  - 聚合计数为 2；里程碑列表、函数「项目组合概览」、动作审计都只含本人项目；
  - 读取员工对象返回 403（没有对应菜单）。
- 没有 FINANCE 标记的用户无法通过任何方式得知金额：
  - 列表、详情、select 中的金额都被遮蔽；
  - 按金额排序、筛选、比较、求和、取最大值、分组、分段分组、用 isNull 探测，全部返回 403；
  - 搜索金额数字搜不到结果；
  - 通过关系读取回款节点、执行项目台账函数，均返回 403。

**数据完整性**
- 9 次对已锁定对象的真实执行全部被拒绝，原因均为中文，执行后 SEY101 的里程碑、节点、约定数量与名称都没有变化。
- 预检不写入审计（G06），被拒绝的执行会留审计（G05）。

**边界处理**
- 分页：pageSize 为 0、超过上限、page 为 0 或非数字时返回 422；页码超出范围时返回空页；最后一页时「下一页」按钮禁用；切换月份后回到第 1 页。
- 搜索：特殊字符、HTML、emoji、只有空格，都正常返回结果。
- 关系遍历：14 类对象的列表与详情，以及 21 种关系的正反向遍历，全部正常。
- 对象集：JSON 格式错误、未知类型、未知字段、数组、嵌套超过 12 层等非法输入，在工作台中都显示清楚的中文错误。

**界面**：五个页签在桌面和手机宽度下都没有整页横向滚动；控制台只有测试故意触发的 422，没有脚本错误。
