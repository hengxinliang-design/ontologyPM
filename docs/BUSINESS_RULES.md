# TSG PM 业务规则与计算口径

> 版本：v2.2（对应本体 2.0.2）· 2026-10-26
> 来源：业务方整理的《TSG PM 业务规则与计算口径说明》。本版把每条规则落到本体中的对象、属性、函数或参数上，并合入了 7 项经确认的口径优化，见第 10 节。

**一句话说明：所有口径只在一处定义。** 可调的数值（工时、阈值、停滞天数、丢单状态、内部代码）保存在本体对象「运营口径参数」（OperatingPolicy）里；计算方法写在对应属性的「来源」说明和规则代码里。所以页面、PM Assistant 和 API 读到的是同一个数。

表中「本体位置」一列的写法：`对象.属性` 表示对象属性，`函数名()` 表示本体函数，`OperatingPolicy.xxx` 表示可调参数。

## 1. 数据边界与基本定义

| 规则 | 口径 | 本体位置 |
| --- | --- | --- |
| 关联主键 | 项目编号连接 CRM、工时和人工维护数据。默认只用有效 CRM 数据生成项目；没有匹配 CRM 的工时保留原始记录，不单独生成项目 | `Project.projectNumber`；未建档代码见 `CostObject` |
| 内部代码 | 投入设置中维护的内部非项目代码（默认 TSG999），不计入项目投入和项目利用率，也不出现在项目清单中（本体 7.8.0 起所有指标读同一列表） | `OperatingPolicy.internalCodes` |
| 系统来源 | CRM 合同和销售机会清单、员工工时 Excel；金额、销售人员、工时数字都是来源数据，只读 | 属性 `sourceKind: system` |
| 人工维护 | 项目类型、项目状态、项目经理、计划起止、预算人天、里程碑、回款约定和到账确认；导入不覆盖 | 属性 `sourceKind: manual`，只能经由本体动作写入（原维护接口调用同一动作） |
| 维护要求 | 导入后必须补充的内容：选择项目类型（不能是未分类）；系统实施和 TSnT365 填写初始预算人天；指定项目经理、填写计划开始与结束日期（售前阶段和已结束、已关闭的项目不要求）；至少制定一个里程碑。回款约定须关联里程碑（关联后才生成回款节点）。满足全部要求即「人工维护完整」 | `Project.maintenanceRequirements`、`PaymentTerm.maintenanceRequirements`（元数据）；`Project.maintenanceChecklist`、`maintenanceGapCount`、`maintenanceComplete`；函数 `maintenanceWorklist` |
| CRM 分类与项目类型 | 「CRM 分类」取 CRM 的分类字段，多份合同去重后用「、」合并；「项目类型」是人工维护的交付管理类型。两者不是同一字段 | `Project.category`、`Project.contractType` |
| 人员职责 | CRM 我方签约人或所有者是销售人员；项目经理是独立的人工维护字段，不再用销售人员填充 | `Project.crmOwner`（销售人员）、`Project.projectManager` |

项目类型有五种取值：系统实施、TSnT365、开口合同、售前阶段、未分类。其中系统实施和 TSnT365 保存配置时必须填写预算人天，开口合同不要求。

### 1.1 项目状态

**人工维护的项目状态优先。** 没有人工配置时，系统按合同的来源状态推导；再推导不出，就是「计划中」。推导规则如下：

| 合同来源状态 | 推导出的项目状态 |
| --- | --- |
| 全部为关闭或终止类 | 已关闭 |
| 全部为结束、完成或关闭类 | 结束 |
| 任一份为执行中、进行中等执行类 | 执行中 |
| 全部为暂停类 | 已暂停 |
| 全部为计划类，或无法识别、混合不满足条件 | 计划中 |

当前状态是怎么来的，记录在 `Project.lifecycleSource` 里：人工维护、合同来源状态推导、默认计划中。

### 1.2 商机与项目

销售机会的状态决定它是不是已经签约：

- 状态为「成功」：已签约，进入项目管理范围，`Project.masterCategory` 为「项目」。
- 状态为「跟踪」：仍是商机，售前投入计为在途投入。
- 状态为「失败」或「失效」：商机已结束，售前投入计为沉没成本（见 10.7）。

销售阶段只描述销售过程，不作为转项目的判断依据。商机阶段和签约后的人天按签约日拆分，规则见[投入成本模型](./INVESTMENT_COST_MODEL.md)和 `CostObject`。

## 3. 工时和工作日

| 指标 | 计算方式 | 本体位置 |
| --- | --- | --- |
| 有效工时 | 审批状态为已提交或已确认的工时；已驳回和草稿保留在明细中，但不计入任何统计（项目、员工、资源、部门、投入成本）（本体 5.1.0） | `TimeEntry.countsAsEffort` |
| 员工项目投入占比 | 员工在各项目代码上的有效工时 ÷ 该员工全部有效工时 × 100%（1 位小数），含 TSG999 等内部代码并标为内部，各项合计 100%；累计口径（本体 7.1.0） | `Employee.projectEffortShares` |
| 员工按月查看 | 选择月份后，员工的当月工时条数、填报、确认、参与项目数、项目投入占比和资源健康（利用率、加班占比、连续过载、同期项目数）按该月计算，工时记录和参与项目、成本对象只列该月有效工时；累计值不变。未选月份时，按月的值取最近有工时的月份（本体 7.2.0） | `Employee` 的 period 与 periodic 属性 |
| 工时记录按月查看 | 本体浏览器的工时记录页按工作日期所在月份筛选，打开时默认显示最近有工时的月份，可切换为全部月份；接口不带月份时仍返回全部记录（本体 7.3.0） | `TimeEntry` 的 period（dateProperty = workDate） |
| 里程碑按月份跨度查看 | 选择起始月份（可再选结束月份），列出计划开始至计划完成与该区间有重叠的里程碑；开始日为空按结束日计；不看完成状态（本体 7.4.0） | `Milestone` 的 period（startProperty / endProperty，range） |
| 实际工时 | 有效工时的正常填报工时加加班工时；不以审批通过为前提 | `Project.reportedPersonDays` |
| 客户确认工时 | 只汇总审批状态为 approved 的 approved_hours；Excel 流转完成记录的确认工时等于正常工时加加班 | `Project.customerConfirmedPersonDays` |
| 实际人天 | 实际工时除以项目每人天小时数（默认 8，可在项目配置中修改）；员工统计用 `OperatingPolicy.standardHoursPerDay` | `Project.hoursPerPersonDay` |
| 待确认缺口 | max（实际工时 − 客户确认工时，0），人天缺口再除以适用的每日小时数；已驳回和草稿不在实际工时中，缺口只剩已提交待确认的部分 | `Project.confirmationGapPersonDays` |
| 工作日 | 周一至周五为基础，扣除落在工作日的法定节假日，加上落在周末的调休补班日，起止日期都计入 | `workingCalendar()` |
| 周期基线工时 | 周期工作日乘以标准每日小时数。节假日订阅不可用且没有缓存时，只按周一至周五计算；有旧缓存时用旧缓存并标记过期 | `workingCalendar()` 的 `available`、`stale` |

注意两个「8 小时」的区别：Excel 的「天数换算小时」固定用 8 小时；项目人天换算用项目自己的每人天小时数。所以修改项目设置会改变展示的人天，但不会改变源工时。

## 4. 收入与回款

| 指标 | 规则 | 本体位置 |
| --- | --- | --- |
| CRM 合同总额 | 同一项目下合同/订单总金额之和；开票和 CRM 已回款分别按合同来源字段求和 | `Project.contractValue`、`invoicedAmount`、`crmReceivedAmount` |
| 结算方式 | 项目类型为开口合同，或开票/回款金额超过合同总额时，按工作量结算；否则按合同额结算 | `Project.revenueSettlementBasis` |
| 回款率（合同额结算） | CRM 已回款 ÷ 合同总额 × 100%；总额不大于 0 时不显示比例；页面比例限制在 0%–100%，金额照实显示 | `projectPaymentStatus()` |
| 待回款 | 合同额结算：max（合同总额 − CRM 已回款，0）；工作量结算：max（CRM 开票 − CRM 已回款，0） | `Project.outstandingReceivableAmount` |
| 签约年度 | 合同的签约年度是 CRM「签约时间」的年份，没有签约时间的合同不属于任何年度；项目的签约年度取它最早一份合同的年份（追加合同不改变项目年度，金额按合同各自的年度统计）；只有商机的项目没有签约年度（本体 5.4.0） | `Contract.signedYear`、`Project.signedYear` |
| 客户年度汇总 | 按签约年度和客户汇总合同数、项目数、新签合同额及这些合同至今的 CRM 开票、回款；开票、回款按签约年度归集，不是该年实际到账（到账年度看部门经营）。客户的「本年合同总额 / 本年签订合同的累计回款 / 本年签订合同的累计开票」取服务器当前日期所在年度（7.5.0 改名：是本年签订合同至今的累计值，不是当年到账） | `customerAnnualSummary()`、`Customer.currentYearContractValue` 等 |
| 客户最近签订 | 该客户合同/订单签订日期的最大值；商机的预计签单日期不参与，没有合同时为空（本体 5.4.1） | `Customer.latestSignedAt` |
| 客户汇总金额 | 客户的合同总额、已回款、已开票分别是该客户全部合同/订单的 CRM 总金额、回款金额、开票金额之和；商机不计入，空金额按 0；不含回款节点的人工到账（本体 5.3.0） | `Customer.totalContractValue`、`totalReceivedAmount`、`totalInvoicedAmount` |
| 确认收入 | 随人天经营口径暂停（本体 4.0.0），见 11.1；系统目前不提供确认收入 | — |
| 回款节点 | 人工约定和到账确认独立于 CRM 实际回款；节点数、计划金额、实际金额单独汇总，不覆盖 CRM 金额 | `PaymentNode` |
| 回款约定数与回款节点数 | 回款节点由关联了里程碑的回款约定产生（6.0.0 起不再独立新建回款节点；存量的独立节点和里程碑上的历史回款事件仍计入）；回款约定未关联里程碑时还没有回款节点。项目同时显示回款约定数、待关联回款约定数和回款节点数（本体 5.5.0） | `Project.paymentTermCount`、`unlinkedPaymentTermCount`、`paymentNodeTotal` |
| 关联约定的里程碑 | 里程碑只有关联回款约定时才产生回款节点：金额取约定金额，日期取里程碑计划完成日，修改计划完成日时回款日期随之更新（已到账的不变）。7.0.0 起不能在里程碑上单独填写回款日期和金额；已有的历史回款事件保留，关联约定后被替换。表单选中约定时显示约定金额和回款比例 | `createMilestone`、`editMilestone` |

工作量结算的项目不显示按框架额计算的回款百分比，也不参与预算规则；但里程碑和回款节点逾期、工时确认缺口仍然纳入风险（见 10.5）。

### 4.1 回款约定

回款约定是合同里写明的回款条款，例如「首付款 30%」。它是本体对象 `PaymentTerm`：

- 可以关联一个里程碑。关联后，系统以里程碑的计划结束日期生成或更新对应的回款节点。
- 已到账的回款节点受保护：编辑约定不会改动已到账的节点，也不能取消关联或删除。在本体中执行「编辑回款约定」时，已到账的约定直接锁定。
- 列表里的节点完成数是人工确认结果，不代表 CRM 回款自动匹配到了某个约定。
- 删除是逻辑删除（本体 7.6.0）：删除里程碑、回款约定、回款节点时只标记失效（记录删除时间和删除人），数据保留，可在审计日志追溯；失效记录不再出现在任何页面、统计和推导中。删除里程碑会让它的回款节点一并失效，回款约定解除关联后保留，可再关联到新的里程碑。管理干预不能删除，只能关闭。

项目列表只显示一条「下一回款约定」：优先取关联未完成里程碑、尚未到账且有计划日期的约定中日期最早的；没有符合条件的，按最近更新时间回退。另外显示的「下个回款节点」按所有未到账节点的计划日期最早者确定，两者不一定相同。

## 5. 项目预算与运营监控

| 指标 | 公式或规则 | 本体位置 |
| --- | --- | --- |
| 预算工时 | 预算人天 × 项目每人天小时数 | `Project.plannedPersonDays` |
| 计划月数 | 结束年月与开始年月的自然月差加 1；跨月不足整月也算涉及的自然月 | `projectHealthForPeriod()` |
| 月均预算 | 预算人天 ÷ 计划月数；缺预算或计划日期时不计算 | 同上 |
| 本期与累计投入 | 本期是统计月份范围内的人天之和；累计是截至统计结束月的人天之和 | 同上 |
| 上期投入 | **紧邻本期、月数相同的前一个期间**的人天之和（见 10.2） | 同上 |
| 参与人数 | 本期和累计分别统计有工时的人员去重数，按员工 ID，没有 ID 时按姓名 | 同上 |
| 燃尽率与剩余预算 | 燃尽率 = 累计实际人天 ÷ 预算人天 × 100%；剩余预算 = 预算人天 − 累计实际人天，可为负 | 同上 |
| 预算耗尽预测 | 统计期月均投入 = 本期投入 ÷ 统计月数；剩余月数 = 剩余预算 ÷ 月均投入；从统计结束月起按向上取整的月数推算耗尽月。无预算、无本期投入、已耗尽、已超预算分别给出提示。**这不是项目交付完工预测** | 同上 |

月度趋势：本期和上期都为 0 时是「暂无记录」；上期为 0 而本期有投入是「新增投入」；否则变化率 =（本期 − 上期）÷ 上期，≥ 10% 为上升，≤ −10% 为下降，其余为持平。

## 6. 风险与健康

### 6.1 项目风险

| 等级 | 条件 |
| --- | --- |
| 严重 | 预算使用率超过 100%；未完成里程碑逾期；未到账回款节点逾期 |
| 关注 | 未完成/未关闭项目的预算使用率达到**预算关注线**；项目类型未设置；系统实施、TSnT365 未设置预算；计划中或执行中项目没有里程碑；存在工时确认缺口 |
| 健康 | 没有任何风险原因 |

里程碑或回款到期当天及未来 7 天显示临近提示；逾期按自然日计算。工作量结算的项目不参与两条预算规则。本体位置：`Project.riskLevel`、`Project.riskReasons`、`projectRiskAssessment()`。

### 6.1a 管理干预（本体 8.0.0，D31–D34）

- 在项目详情中发起和更新，权限沿用项目维护：PMO、管理员、项目经理（只限本人项目）。
- 发起时截止日期必填；负责人不填时取项目经理；类型为进度、资源、回款、客户、质量、其他（`management`，缺省）。
- **已逾期**：状态不是已关闭，且截止日期早于今天（当天不算）。没有截止日期的存量干预不算逾期。
- 每条逾期干预在项目「待处理事项」中提醒一次（关注级）；**不计入风险等级和风险原因**（D33）。
- 关闭后锁定，不能重新打开或删除；关错了重新发起。
- 本体位置：`Intervention.overdue`、`Project.openInterventions`、`Project.overdueInterventions`、动作 `openIntervention`、`updateInterventionStatus`；构建包 [2026-11-01-intervention-loop](ontology-builds/2026-11-01-intervention-loop.yaml)。

### 6.2 运营监控预警

| 预警 | 条件 |
| --- | --- |
| 待维护预算 | 没有预算人天 |
| 已超预算 | 剩余预算小于 0 |
| 高风险 | 未超预算，且燃尽率 ≥ **预算高风险线**（默认 90%） |
| 需关注 | 燃尽率 ≥ **预算关注线**（默认 80%）且低于高风险线 |
| 工作量结算 | 按工作量结算的项目，不做预算预警 |
| 正常 | 其余有预算的情况 |

**两套阈值已经统一为一套**：项目风险的「关注」和运营监控的「需关注」都用 `OperatingPolicy.budgetAttentionPercent`（见 10.1）。

### 6.3 综合健康

按以下顺序判定，先满足的优先：

1. 所有合同来源状态均为结束类，且统计期仍有投入：**额外投入**。
2. 已超预算。
3. 缺预算：**无基线**。
4. 预警为高风险或需关注，或项目风险为严重或关注：**需关注**。
5. 其余：**健康**。

## 7. 员工利用率与资源调剂

员工项目工时利用率 = 统计期项目实际工时 ÷ 同期工作日基线工时 × 100%。内部代码（投入设置维护，默认 TSG999）的工时不计入项目利用率，作为可转换资源单独保留。本体 7.8.0 起，利用率、工时评价、调剂建议与资源健康只在 `derivations/resources.py` 实现一次（函数 `resourceOperations()`、`employeeWorktimeAssessment()`、`resourceHealth()`）。员工**按员工 ID 汇总**，没有 ID 时才按姓名（见 10.4）。

| 参数（`OperatingPolicy`） | 默认值 | 用途 |
| --- | --- | --- |
| 标准每日小时数 | 8 | 周期基线工时 |
| 关注线 / 最低线 / 优秀线 / 过载线 | 60% / 75% / 90% / 100% | 必须满足 关注 < 最低 < 优秀 < 过载 |
| 年工作日、年/月/季度基线 | 230 天、1840/153/460 小时 | 仅作参考，不等同于当期日历基线 |

| 员工状态 | 条件 | 资源负荷 | 条件 |
| --- | --- | --- | --- |
| 工时充足 | > 优秀线 | 本月负荷过高 | > 过载线（单月） |
| 基本达标 | > 最低线 | 负荷较高 | > 优秀线 |
| 需要关注 | > 关注线 | 安排基本均衡 | 其余 |
| 严重不足 | ≤ 关注线 | 可适度支持 | ≤ 最低线 |
| | | 可优先调剂 | ≤ 关注线 |

边界值落入较低一档。「本月负荷过高」只看单月，与资源健康的「持续过载」（连续 N 个月）不同（需求基线 D13）。可调剂人天 = max（周期基线工时 × 最低线 − 项目实际工时，0），再与内部代码工时取较大值，除以每日标准小时数。**负荷较高或过高的人员不计内部可调剂工时**（见 10.6）。

### 11.1 项目经营

| 指标 | 公式或规则 | 本体位置 |
| --- | --- | --- |
| 暂估收入 | 合同额 ÷（1 + 税率）− 外部采购 − 商务费用；税率默认 6%，项目可覆盖 | `Project.estimatedRevenue` |
| 可用成本 | 暂估收入 ×（1 − 目标毛利率）；目标毛利率默认 30%，项目覆盖时必须写原因 | `Project.availableCost` |
| 可支配人天 | 可用成本 ÷ 合同人天单价 | `Project.disposablePersonDays` |
| 动态成本 | 已用人天 × 合同人天单价；已用人天含加班、不以审批为前提，内部代码不计入 | `Project.dynamicCost` |
| 当前暂估毛利率 | （暂估收入 − 动态成本）÷ 暂估收入 | `Project.estimatedGrossMarginPercent` |
| 预计完工毛利率 | （暂估收入 −（已用人天 + 剩余人天）× 单价）÷ 暂估收入；剩余人天取项目经理估算，没有时取 max（预算 − 已用，0），项目结束后为 0 | `Project.forecastGrossMarginPercent` |
| 确认收入 | 按里程碑：已到账回款节点 ÷（1 + 税率）− 扣减项 × 已到账比例；按工作量：CRM 开票 ÷（1 + 税率）；售前与未分类不确认 | `Project.confirmedRevenue` |
| 确认毛利率 | （确认收入 − 动态成本）÷ 确认收入；只展示，不单独判定 | `Project.confirmedGrossMarginPercent` |
| 成本超前 | 成本进度（动态成本 ÷ 可用成本）− 收入确认进度（确认收入 ÷ 暂估收入），单位百分点；首个回款节点计划日前为宽限期 | `Project.costAheadPoints` |
| 经营状态 | 缺合同额或单价 → 无基线；动态成本超过可用成本，或成本超前达到预警线（默认 20）且过了宽限期 → 超标；预计完工毛利率低于目标 → 预警；其余达标 | `Project.economicsStatus` |
| 回款对账 | 节点到账合计与 CRM 已回款不一致时提示差额，确认收入仍以节点为准 | `Project.economicsReasons` |

用财务提供的 SEY 示例核对：SEY 客户合计暂估毛利率 8.27%，但 SEY101 为 −34.61%、成本超前 142.31 个百分点，判超标；SEY103 确认毛利率 25.06%，但成本超前只有 3.53，仍为达标。

只评估当月填报了工时的员工，按严重程度取第一项，同时列出全部成立的项（`resourceHealth()`、`Employee.healthStatus`）：

| 状态 | 规则 |
| --- | --- |

### 11.4 年度经营计划与策略信号

年度经营指标口径（本体 7.10.0，需求基线 D22–D29；财年为自然年，本期只有一个部门）：

| 指标 | 口径 | 本体位置 |
| --- | --- | --- |
| 经营收入（税前） | 当年到账的回款：已到账回款节点、到账日期在当年且不晚于统计月份末，含往年签约合同的回款 | `departmentOperatingReview()` 的 `collections` |
| 经营收入（税后） | 税前收入 ÷ (1 + 增值税率)；增值税率为运营口径参数，默认 6% | `OperatingPolicy.defaultTaxRatePercent` |
| 合同额 | 当年签约的全部合同金额（CRM 合同总金额，含税），不分税前税后 | `new_contracts` |
| 经营成本 | 财务线下提供、按月录入的六类成本合计：人工成本、绩效奖金、差旅费、外包成本、培训成本、其他；某月未录入不等于 0 | `OperatingCost`，动作「录入经营成本」 |
| 毛利润 | 税后收入 − 经营成本，收入与成本都截至最近一个已录成本的月份（标明截止月份） | `gross_profit` |
| 毛利率 | 毛利润 ÷ 税后收入（同一截止月份） | `gross_margin` |

年度计划按年度关联三类对象（本体 7.11.0，D30）：本年签约合同（合同额的来源）、本年到账回款节点（经营收入的来源）、本年经营成本，在本体浏览器中可从年度计划逐条追到构成指标的合同、回款和成本，也可从这些对象反查所属年度计划。

年初录入经营收入目标（税前，原「回款目标」）、合同额目标和经营成本目标；税后收入、毛利润、毛利率目标由系统推算。经营成本是越低越好的指标：完成率超出时间进度加容差为「超支」。项目投入人天、人员编制、利用率作为资源指标保留。

- 年度目标人工维护（`AnnualOperatingPlan`，动作「设定年度经营计划」或部门经营页）。累计指标的完成率与时间进度（已过月份 ÷ 12）比较，落后超过容差（默认 5 个百分点）为落后；毛利率、利用率、人数直接与目标比较。
- 策略信号按优先级给出，每条附依据，只作建议：推动验收回款（回款节点逾期，或交付已结束仍有未到账节点）> 控制成本（超标项目达到 2 个，或部门预计完工毛利率低于目标）> 招聘或外部支援（未来三个月需求超过产能，且最近两月利用率都高于优秀线）> 争取新合同（在手合同覆盖明年产能低于 50%，或最近一月利用率不高于关注线）> 释放资源（可支配人天用完或计划次月结束且仍有投入）> 保持。

## 12. 角色与数据范围（本体 7.7.0）

账号有一个角色，角色决定数据范围和默认菜单，管理员可以再逐个账号增减菜单（需求基线 D9）：

| 角色 | 数据范围 | 默认菜单 |
| --- | --- | --- |
| 管理员 | 全部项目 | 全部；唯一能在本体浏览器执行动作的角色 |
| PMO | 全部项目 | 项目管理、投入、部门经营、资源、CRM 查询、员工工时、CRM 上传 |
| 部门负责人 | 全部项目 | 项目管理（只读）、部门经营、资源、投入、CRM 查询 |
| 项目经理 | 本人项目 | 项目管理；只能有「项目管理」「项目管理（只读）」 |
| 分析人员 | 全部项目 | 项目管理（只读）、部门经营、资源、投入、CRM 查询、本体浏览器 |

- **本人项目**：项目的「项目经理」字段与账号的「姓名」完全相同（D10）。姓名在账号间唯一；项目经理字段为空或填的名字没有账号时，没有项目经理能看到该项目，由 PMO 维护。项目换了项目经理，下一次请求即按新名字计算。
- **项目经理能看到什么**：本人项目及其里程碑、回款约定、回款节点、管理干预，金额可见；员工、工时记录、客户、合同等对象不可见，项目页面中按员工的工时被遮蔽（D11）。PM Assistant 以项目经理本人的权限查询本体，只能问到本人项目（G5）。
- **本体浏览器**：动作只有管理员能执行；其他人在本体浏览器只读，日常维护在业务页面进行（D12）。
- 本次升级前已有的非管理员账号记为「未设角色」：保留原菜单，数据范围为全部项目，由管理员逐个设定角色。
